## Overview

**What this is.** Headscale's HTTP API is the JSON mapping of its gRPC service `headscale.v1.HeadscaleService`. This
spec's `info.title` is `headscale/v1/headscale.proto`, `swagger` is `2.0`, there is a single tag `HeadscaleService`,
and every `operationId` is `HeadscaleService_*` (for example `HeadscaleService_ListNodes`) — the signature of a spec
generated by grpc-gateway from a proto file. In other words: **the spec describes the HTTP half only**. If Headscale
also exposes capabilities reachable only over native gRPC, this spec does not contain them (to be confirmed; it
cannot be determined from the spec itself).

**Base path.** Every endpoint lives under `/api/v1`.

**Authentication.** All calls use `Authorization: Bearer <API key>`. Note that this spec has **no**
`securityDefinitions` block: the auth scheme is not read from the spec but from Headscale's actual behaviour and from
this project's code (`app/server/headscale/api/transport.ts:91` adds the header to every request). Requests from this
project also carry `Accept: application/json` and `User-Agent: Headplane/<version>`.

**Where the key comes from.** Create one on the Headscale server with the CLI, for example
`headscale apikeys create --expiration 90d`. After creation the one-time plaintext is only visible on Headplane's
**Settings -> API keys** page (`POST /api/v1/apikey`) — but that page itself needs a working key, so **the first key
must come from the CLI**. This project reads the key the server uses from the `headscale.api_key` config entry, falling
back to the deprecated `oidc.headscale_api_key` (`app/server/context.ts:56-58`). The key a user types when logging
into Headplane is unrelated: that is a separate, session-scoped credential.

**The gRPC / HTTP split.** The spec contains no gRPC-only entries; every `operationId` maps onto the same `/api/v1`
paths. Whether this operator's deployment exposes Headscale's native gRPC listener (port `50443` by default) cannot be
determined from the spec — **to be confirmed**. This project uses HTTP only.

**The live Swagger UI.** `https://headscale.example.com/swagger`; its "Explore" box points at
`https://headscale.example.com/swagger/v1/openapiv2.json`. Substitute your own address for `headscale.example.com`.
This document uses placeholders throughout and records no real domain, IP address or key.

**One trap in the spec.** The `summary` fields are not endpoint descriptions: they are section comments copied from
the proto file, such as `"summary": "--- ApiKeys start ---"`, `"--- Node start ---"`, `"--- Health start ---"`. The
capability column on this page was written from each `operationId` and the endpoint's semantics, not copied from
`summary`.

## Nodes

### GET /api/v1/node

- Parameters: `user` (query, string, optional) filters by user name.
- Response: `{ nodes: Node[] }`. Fields of interest on `Node`: `id` (uint64 string), `machineKey`, `nodeKey`,
  `discoKey`, `ipAddresses[]`, `name`, `user` (nested `User`), `lastSeen`, `expiry`, `preAuthKey`, `createdAt`,
  `registerMethod` (enum `REGISTER_METHOD_UNSPECIFIED` / `_AUTH_KEY` / `_CLI` / `_OIDC`), `online`,
  `approvedRoutes[]`, `availableRoutes[]`, `subnetRoutes[]`, `tags[]`; `givenName` is marked deprecated in the spec.
- Note: since 0.28 `tags` is a flat array; before that it was `forcedTags`/`validTags`/`invalidTags`, which this
  project merges itself based on a capability flag (`api/resources/nodes.ts:41-47`).
- Preconditions: none.
- curl:

  ```bash
  curl -sS -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    "https://headscale.example.com/api/v1/node"
  ```

### GET /api/v1/node/{nodeId}

- Parameters: `nodeId` (path, uint64 string, required).
- Response: `{ node: Node }`, same fields as above.
- Preconditions: `nodeId` must come from the list first; this project takes it straight from the route parameter on
  `/machines/:id`.
- curl:

  ```bash
  curl -sS -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    "https://headscale.example.com/api/v1/node/$NODE_ID"
  ```

### DELETE /api/v1/node/{nodeId}

- Parameters: `nodeId` (path, uint64 string, required).
- Response: the empty object `{}`.
- Preconditions: irreversible; this project asks for confirmation in the delete dialog.
- curl:

  ```bash
  curl -sS -X DELETE -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    "https://headscale.example.com/api/v1/node/$NODE_ID"
  ```

### POST /api/v1/node/register

- Parameters: `user` (query, string, marked optional in the spec, required in practice) and `key` (query, string,
  marked optional in the spec, required in practice).
- Response: `{ node: Node }`.
- Preconditions and divergence: this project's client sends **both** the query string and a JSON body
  (`api/resources/nodes.ts:69-87`); the code comment says Headscale expects both, but the spec declares query
  parameters only, so the **body is undeclared** — marked as to be confirmed. From 0.29 the `key` must carry the
  `hskey-authreq-` prefix; earlier versions want it stripped (capability `registerKeyIncludesAuthReqPrefix`).
- curl:

  ```bash
  curl -sS -X POST \
    -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    -H "Content-Type: application/json" \
    -d '{"user":"$USER_NAME","key":"$REGISTRATION_KEY"}' \
    "https://headscale.example.com/api/v1/node/register?user=$USER_NAME&key=$REGISTRATION_KEY"
  ```

### POST /api/v1/node/{nodeId}/approve_routes

- Parameters: `nodeId` (path, uint64, required); body `{ routes: string[] }` (an array of CIDR strings).
- Response: `{ node: Node }`.
- Preconditions: `routes` is a **full replacement**, not an increment. This project merges "already approved" with
  "newly selected" before submitting, which is why it reads the node's current `approvedRoutes` first (it calls
  `api.nodes.get` in `machine-actions.ts`).
- curl:

  ```bash
  curl -sS -X POST \
    -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    -H "Content-Type: application/json" \
    -d '{"routes":["10.0.0.0/24","192.168.1.0/24"]}' \
    "https://headscale.example.com/api/v1/node/$NODE_ID/approve_routes"
  ```

### POST /api/v1/node/{nodeId}/expire

The spec gives one endpoint three call shapes, all of whose parameters live in the query string:

| Shape              | Parameters                     | Meaning                             |
| ------------------ | ------------------------------ | ----------------------------------- |
| Expire now         | none                           | Sets the expiry to the current time |
| Toggle expiry      | `disableExpiry=true` / `false` | `true` means the node never expires |
| Explicit timestamp | `expiry=<RFC3339>`             | Sets an explicit expiry timestamp   |

- Parameters: `expiry` (query, string/date-time, optional) and `disableExpiry` (query, boolean, optional).
- Response: `{ node: Node }`.
- Preconditions: `expiry` exists in every version Headplane supports (0.27.0+); `disableExpiry` requires **0.29.0+**
  (capability `keyExpiryCanBeDisabled`). To kick a node off an older server, use the no-parameter shape. Note that
  `expiry` is a query parameter rather than a body field, because the proto carries no `body` annotation.
- curl:

  ```bash
  # Expire immediately
  curl -sS -X POST -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    "https://headscale.example.com/api/v1/node/$NODE_ID/expire"

  # Never expire (requires Headscale 0.29.0+)
  curl -sS -X POST -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    "https://headscale.example.com/api/v1/node/$NODE_ID/expire?disableExpiry=true"

  # Explicit expiry timestamp
  curl -sS -X POST -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    "https://headscale.example.com/api/v1/node/$NODE_ID/expire?expiry=2030-01-01T00:00:00.000Z"
  ```

### POST /api/v1/node/{nodeId}/rename/{newName}

- Parameters: `nodeId` (path, uint64, required) and `newName` (path, string, required).
- Response: `{ node: Node }`.
- Preconditions: the `nodeId` must be fetched first, as above. The client applies `encodeURIComponent` to `newName`
  (`api/resources/nodes.ts:102`), so escape names containing spaces or non-ASCII characters yourself when calling by
  hand.
- curl:

  ```bash
  curl -sS -X POST -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    "https://headscale.example.com/api/v1/node/$NODE_ID/rename/$NEW_NAME"
  ```

### POST /api/v1/node/{nodeId}/tags

- Parameters: `nodeId` (path, uint64, required); body `{ tags: string[] }`.
- Response: `{ node: Node }`.
- Preconditions: again a full replacement — an empty array clears the tags. Tags must be declared in the policy, which
  is why this project's tags dialog points users at `/acls`.
- curl:

  ```bash
  curl -sS -X POST \
    -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    -H "Content-Type: application/json" \
    -d '{"tags":["tag:server"]}' \
    "https://headscale.example.com/api/v1/node/$NODE_ID/tags"
  ```

### POST /api/v1/node/backfillips

- Parameters: `confirmed` (query, boolean, optional; the spec carries **no** description, so the semantics are to be
  confirmed).
- Response: `{ changes: string[] }`; the spec does not describe the format of the strings in `changes` — to be
  confirmed.
- Status: **missing**; there is no call site in the code.
- Typical use: after upgrading from a very old Headscale, some nodes lack IP addresses and need a one-off backfill.
- curl:

  ```bash
  curl -sS -X POST -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    "https://headscale.example.com/api/v1/node/backfillips?confirmed=true"
  ```

## Policy

### GET /api/v1/policy

- Parameters: none.
- Response: `{ policy: string, updatedAt: string(date-time) }`.
- Preconditions: none.
- curl:

  ```bash
  curl -sS -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    "https://headscale.example.com/api/v1/policy"
  ```

### PUT /api/v1/policy

- Parameters (body): `policy` (string; semantically required, though the spec does not mark it required).
- Response: `{ policy: string, updatedAt: string }`.
- Preconditions: the write takes effect immediately; this project calls `/policy/check` before saving.

- Response: the **empty object** `{}` on success (the spec's `v1CheckPolicyResponse` has no fields); a `rpcStatus`

- Preconditions: none. This project wraps every non-2xx upstream response as a 502

## Pre-auth keys

### GET /api/v1/preauthkey

- Parameters: the spec lists **none**. This project still sends `?user=<user id>` on its pre-0.28 fallback path

- Response: `{ preAuthKeys: PreAuthKey[] }`. Fields: `user` (nested `User`, null for tag-only keys), `id`, `key`,
  `reusable`, `ephemeral`, `used`, `expiration`, `createdAt`, `aclTags[]`.
- Preconditions: none.
- curl:

  ```bash
  curl -sS -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    "https://headscale.example.com/api/v1/preauthkey"
  ```

### POST /api/v1/preauthkey

- Parameters (body): `user` (uint64 string, optional — omit it for an ownerless tag-only key on 0.28+), `reusable`

- Response: `{ preAuthKey: PreAuthKey }`, where `key` is the plaintext key.
- Preconditions: machines that use the key inherit `aclTags`; the agent relies on exactly this to tag itself


### POST /api/v1/preauthkey/expire

- Parameters (body): the spec declares `id` (uint64 string) only.
- Divergence: Headscale before 0.28 requires `{ user, key }`, and `user` must be a **uint64 user id** — passing a user
  name fails with `proto: invalid value for uint64 field user` (code comment,
  `api/resources/pre-auth-keys.ts:68-70`). That legacy payload is **not** in this spec; this project switches between
  the two based on a capability flag.
- Response: the empty object `{}`.
- Preconditions: the key's `id` (0.28+) or the `user` plus the plaintext `key` (earlier versions) — which is exactly
  why this project keeps `listForUser` around for old servers: the plaintext key must come from the list.
- curl:

  ```bash
  # Headscale 0.28+
  curl -sS -X POST \
    -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    -H "Content-Type: application/json" \
    -d '{"id":"$PREAUTH_KEY_ID"}' \
    "https://headscale.example.com/api/v1/preauthkey/expire"
  ```

### DELETE /api/v1/preauthkey

- Parameters: `id` (query, uint64 string, optional).
- Response: the empty object `{}`.

## API keys

### GET /api/v1/apikey

- Parameters: none.
- Response: `{ apiKeys: ApiKey[] }`. Fields: `id`, `prefix`, `expiration`, `createdAt`, `lastSeen`.
- Preconditions: none. This endpoint has the most call sites in the project: Settings -> API keys
  (`settings/api-keys/overview.tsx:48`), Settings -> System diagnostics (`settings/system/overview.tsx:182`),
  validating the key a user typed at login (`auth/login/action.ts:62`), the `/overview` counters, the layout keepalive
  (`layout/app.tsx:67`) and the alerts service (`alerts/service.server.ts:214`).
- curl:

  ```bash
  curl -sS -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    "https://headscale.example.com/api/v1/apikey"
  ```

### POST /api/v1/apikey

- Parameters (body): `expiration` (date-time).
- Response: `{ apiKey: string }` — the plaintext is returned **exactly once** and can never be read back.
- Preconditions: a valid key must already exist (chicken and egg), so bootstrap with the CLI.
- curl:

  ```bash
  curl -sS -X POST \
    -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    -H "Content-Type: application/json" \
    -d '{"expiration":"2030-01-01T00:00:00Z"}' \
    "https://headscale.example.com/api/v1/apikey"
  ```

### POST /api/v1/apikey/expire

- Parameters (body): `prefix` (string), `id` (uint64 string).
- Response: the empty object `{}`.
- Preconditions: `prefix` must be the **raw prefix** Headscale stored (12 characters for 0.28+ keys); the list endpoint
  returns a masked form that cannot be echoed back (code comment, `api/resources/api-keys.ts:15-19`). The spec does not
  say whether `prefix` is masked — the code is authoritative here, and the spec side is marked as to be confirmed.
- curl:

  ```bash
  curl -sS -X POST \
    -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    -H "Content-Type: application/json" \
    -d '{"prefix":"$API_KEY_PREFIX"}' \
    "https://headscale.example.com/api/v1/apikey/expire"
  ```

### DELETE /api/v1/apikey/{prefix}

- Parameters: `prefix` (path, string, required) and `id` (query, uint64 string, optional). Which of the two identifiers
  wins when both are supplied is not documented in the spec — to be confirmed.
- Response: the empty object `{}`.
- Status: **missing**.
- curl:

  ```bash
  curl -sS -X DELETE -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    "https://headscale.example.com/api/v1/apikey/$API_KEY_PREFIX"
  ```

## Authentication and registration

This group shares a precondition worth stating up front: **the spec has no endpoint that lists pending registration
requests**. An `authId` can therefore only come from Headscale's logs or CLI, or from the authorization URL that tsnet
prints. This project's agent extracts the authId from a failed login's stderr with a regular expression
(`app/server/hp-agent.ts:172-179`). Without a list endpoint, any UI built on an authId lacks a data source.

### POST /api/v1/auth/approve

- Parameters (body): `authId` (string).
- Response: the empty object `{}`.
- Preconditions: a valid `authId`. This project only calls it for agent auto-approval and offers no manual entry
  point; the page is **Settings -> Agent** (state driven by `hp-agent.ts`).
- curl:

  ```bash
  curl -sS -X POST \
    -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    -H "Content-Type: application/json" \
    -d '{"authId":"$AUTH_ID"}' \
    "https://headscale.example.com/api/v1/auth/approve"
  ```

### POST /api/v1/auth/register

- Parameters (body): `user` (string) and `authId` (string).
- Response: `{ node: Node }`.
- Status: **missing**; with no pending list, the UI has no way to choose which registration to target.
- curl:

  ```bash
  curl -sS -X POST \
    -H "Authorization: Bearer $HEADSCALE_API_KEY" \
    -H "Content-Type: application/json" \
    -d '{"user":"$USER_NAME","authId":"$AUTH_ID"}' \
    "https://headscale.example.com/api/v1/auth/register"
  ```

### POST /api/v1/auth/reject

- Parameters (body): `authId` (string).
- Response: the empty object `{}`.
- Status: **missing**; same reason as above.
- curl:

  ```bash
  curl -sS -X POST \
  ```

## Missing and partial implementations

Priority: **P1** worth doing soon, **P2** valuable but can wait, **P3** optional or best not done. Every conclusion
below was checked against an actual call site in the code rather than inferred from memory.

| Endpoint                           | Status  | Recommendation                                                                                                                                        | Priority |
| ---------------------------------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| `GET /api/v1/node` (`user` filter) | Partial | Server-side filtering is worth considering for very large tailnets; the UI filters client-side today, so nothing is functionally missing              | P3       |
| `POST /api/v1/node/backfillips`    | Missing | Add a confirmed, one-off repair entry under Settings -> System (nodes missing IPs after an old-database upgrade); confirm `confirmed` semantics first | P2       |
| `DELETE /api/v1/preauthkey`        | Missing | The existing "revoke" already covers the main need via expire; if implemented, restrict deletion to expired or already-used keys                      | P3       |
| `DELETE /api/v1/apikey/{prefix}`   | Missing | Same as above — expire already invalidates the key immediately; if implemented, note the spec's optional `id` query parameter                         | P3       |
| `POST /api/v1/auth/register`       | Missing | The spec has no pending-registration list, so the UI has no data source; leave it out unless the operator pastes an authId by hand                    | P3       |
| `POST /api/v1/auth/reject`         | Missing | Same reason; and the result cannot be reviewed in the UI afterwards                                                                                   | P3       |
| `POST /api/v1/debug/node`          | Missing | Best left unimplemented                                                                                                                               | P3       |
| `GET /api/v1/health`               | Missing | The root `/health` already covers this. Add it only when "is the database reachable" must be distinguished; could join Settings -> System diagnostics | P3       |

**Additional findings (not among the four target endpoints above)**

- `POST /api/v1/node/{id}/user`: this project still calls it to move a machine to another user when
  `capabilities.nodeOwnerIsImmutable` is false (Headscale < 0.28) — see `api/resources/nodes.ts:134-143`, surfaced by
  the move dialog and bulk move on `/machines`. That endpoint **no longer exists in this spec** and returns 404 on
  0.28+, which is exactly why the capability flag gates it so strictly. This is a known, intentional spec/code
  divergence for backwards compatibility; changing it is not recommended.
- `GET /version` and `GET /health` (root path): not in this spec, but this project depends on them for capability
  detection and health checking (`api/index.ts:94` and `api/transport.ts:159` respectively).

## How to verify

1. **Open the live Swagger.** Visit `https://headscale.example.com/swagger` and expand the `HeadscaleService` group to
   see all 29 endpoints. When the UI is unavailable, read the spec directly:

   ```bash
   curl -sS https://headscale.example.com/swagger/v1/openapiv2.json | jq '.paths | keys'
   ```

2. **Call an endpoint with curl.** The `Authorization` header is the only requirement; validate the key against a
   read-only endpoint first:

   ```bash
   export HEADSCALE_URL="https://headscale.example.com"
   export HEADSCALE_API_KEY="$HEADSCALE_API_KEY"
   curl -sS -o /dev/null -w '%{http_code}\n' \
     -H "Authorization: Bearer $HEADSCALE_API_KEY" "$HEADSCALE_URL/api/v1/node"
   ```

3. **Common failure modes.**

   | Symptom            | Meaning                                                                                                                                                                                                                                    | What to do                                                                                                      |
   | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- |
   | `401 Unauthorized` | The key is wrong, truncated, expired or revoked. Headplane's login page and Settings -> System report this as an invalid API key                                                                                                           | Reissue with `headscale apikeys create` and update `headscale.api_key`                                          |
   | `403 Forbidden`    | Headscale API keys are admin-level and rarely produce this themselves. More often a reverse proxy (Caddy/Nginx) rejected the request, or Headplane's own permission bits denied it                                                         | Verify by calling the API directly, bypassing the proxy; then check capability flags and the user's role        |
   | `404 Not Found`    | The endpoint does not exist on the connected Headscale version (version gating). For example `POST /api/v1/node/{id}/user` was removed in 0.28+, and `/api/v1/node/backfillips` only appears on newer releases                             | Confirm the version via `/version`; this project derives capability flags from it rather than probing with 403s |
   | `502 Bad Gateway`  | This is Headplane's own wrapper: any non-2xx upstream response is wrapped as a 502, with the real status code carried as `statusCode` and a sanitized one-line summary of the upstream text as `detail` (the raw body stays on the server) | Read `statusCode` from the body to recover the real error instead of debugging a 502                            |

4. **Re-check an "implemented" claim.** First find the `path:` literals in
   `app/server/headscale/api/resources/*.ts` to establish client coverage, then search `app/routes/**` for the matching
   API method name to confirm a UI call site. A wrapper with no call site does not count as implemented.

### Items marked as to be confirmed

- Whether the spec contains gRPC-only capabilities: it cannot be determined from the spec.
- Whether `GET /api/v1/preauthkey` accepts a `user` query parameter: the spec lists none, but the code sends it below 0.28.
- Whether `POST /api/v1/node/register` accepts a JSON body: the spec declares query parameters only, and the code sends both.
- The meaning of `confirmed` on `POST /api/v1/node/backfillips` and the format of the strings in its `changes` response: the spec carries no description.
- Which wins when both `prefix` and the optional `id` are present on `DELETE /api/v1/apikey/{prefix}`: undocumented.
- Whether the `prefix` returned by `GET /api/v1/apikey` is masked: undocumented; this page follows the code comment.
- Whether `id`/`name`/`email` can be combined on `GET /api/v1/user`: undocumented; this project's client enforces mutual exclusivity.
- What `DELETE /api/v1/user/{id}` does when the user still owns nodes: undocumented.
